The human relationship with the organization lives **only** in `organization_memberships`.

### 4.4 `company_profiles` — formal explanation

This sub-section explains `company_profiles` as it stands today, its role as the company-side surface, and the target transition. The target is documented in this gap analysis only; no migration is authored.

- **Primary key and relation.** `company_profiles.profile_id` is a `UUID PRIMARY KEY REFERENCES profiles(id)` (`20260726000007_canonical_identity_access.sql:133-142`). It is a 1:1 per-person extension of `profiles`: every `company_profiles` row is owned by exactly one `profiles` row whose `account_type = 'company'`. There is currently no `organization_id` on `company_profiles`.
- **Relation to `auth.users`.** The owning profile is a row in `profiles` whose `id` mirrors `auth.users.id`. Authentication is on the person, not on the company (D-01, D-02). The person signs in; the per-person `company_profiles` row carries the company identity. The company is not a `profiles` row and never will be (D-01).
- **Identity of the company.** The company identity is the tuple `company_profiles.profile_id` (the person) plus the per-company metadata (`company_name`, `industry`, `website`, `verification_status`). The verification lifecycle is `pending | verified | rejected | suspended`. The `company_name` is the company display name; the website is informational; the industry is a free-text classification.
- **Resources that reference `company_profiles`.** `opportunities.publisher_id` is a `profiles.id` whose `account_type` is `company`; the company-identity reference is **implicit** through the publisher profile. The `opportunities.publisher_id` → `company_profiles.profile_id` join is the de-facto company reference. There is no `opportunities.company_id` column today. `internship_requests.company_id` references `profiles.id` whose `account_type` is `company`. `job_postings.company_id` references `profiles.id` whose `account_type` is `company`. `company_follows.follower_id` / `company_follows.company_id` both reference `profiles.id`. The server actions in `apps/web/src/app/actions/company.ts` and `apps/web/src/app/actions/opportunities.ts` are the application-level company surfaces.
- **Policies.** `company_profiles_select_scope` (own row or verified company), `company_profiles_update_owner` (own row only). The two policies are recorded in `20260726000007_canonical_identity_access.sql:133-142` and reviewed in §13.1.
- **Server actions and routes.** The company surfaces live under `apps/web/src/app/company/{dashboard,profile,empleos,applicants,settings,notifications}/` and the catch-all `company/[...path]/page.tsx`. The server actions in `apps/web/src/app/actions/company.ts:7, 80, 146, 198, 276` use `createAdminClient()` for application status updates and internship request creation.
- **Three current uses of `company_profiles`.**
  1. **As a company owner of resources.** The `opportunities.publisher_id` (for `opportunity_type IN ('job','internship','company_project')`) is the person whose `company_profiles` row exists. Today, "who is the company" is implicit (the per-person `company_profiles` row). After Phase 1B, the canonical company reference is an `organizations` row with `kind = 'company'`, and the company owner is an `organization_memberships` row with `member_role = 'owner'`.
  2. **As a per-person company profile (the human view).** The person fills in the company name, industry, website and verification status. The person is also the person who appears in profile listings, in company searches, and in the company dashboard header.
  3. **As the implicit `organization_id` of a company (today, by convention).** Because every company is a single-person surface today, the `profile_id` doubles as the company id by convention. This convention is the source of the **company_profiles transition**: the mandate replaces the convention with an explicit `organizations` row and an explicit `organization_memberships` row.
- **Target destination.** The `company_profiles` row becomes a view or is replaced by an `organizations` row with `kind = 'company'`. The transition is **after** the inbound FKs (`opportunities.publisher_id` for the three corporate types, `internship_requests.company_id`, `job_postings.company_id`, `company_follows.*_id`) have been re-pointed or kept as transitional identifiers. The `organization_memberships` row with `member_role = 'owner'` is the canonical owner reference. **The canonical `organizations` row has no `profile_id` column** (REV 4.2 FINAL DOCUMENTARY CLEANUP / AUDIT PENDING; supersedes the prior "backfill / adapter column" framing). The physical legacy column `company_profiles.profile_id` is a **physical legacy column in the adapter table**; it is **not** introduced as canonical on the `organizations` row. No future policy reads `organizations.profile_id`.
- **Conversion of the admin to a membership owner.** The current `company_profiles.profile_id` (the admin) becomes a membership row in `organization_memberships` with `member_role = 'owner'`, `status = 'active'`. The admin is **not** re-created; the existing profile row is **membership-bound** to the new `organizations` row. The "owner active" invariant (§5.4) is preserved: exactly one active owner per company.
- **Compatibility during the transition — single coherent option (Option A: physical adapter table).** The compatibility option is **single and coherent**: **`company_profiles` remains a physical table during the transition** (the "adapter"); the canonical data migrates to `organizations(kind = 'company')`; the current `profile_id` admin becomes an active `owner` membership in `organization_memberships`; the stable mapping between the legacy `company_profiles.profile_id` and the new `organizations.id` (and the new `organization_memberships.organization_id`) is preserved. The adapter is **not** converted to a view immediately. The view conversion (or table drop) is performed only **after** the inbound FKs, the RLS predicates and the application consumers have been migrated and verified (FK-to-view blocker, §4.3). The current state is **not** a view; the target is **not** an immediate view. The chosen option is Option A because it centralizes the company identity in `organizations` while keeping the legacy RLS and the legacy server actions byte-identical against the physical `company_profiles` table for the duration of the migration. The "view" framing in earlier revisions is **superseded** by this Option A framing: a view is the end-state of Option A only after the consumers and FKs are migrated.
- **No automatic creation of an organization per `company_profiles` row.** The migration **must not** create an `organizations` row per `company_profiles` row by default. The backfill is reviewed and qualified against the following classes: **duplicates** (two `company_profiles` rows that represent the same legal entity); **shared accounts** (multiple persons on one `company_profiles` row, which the current 1:1 schema forbids but the data may show if `profile_id` was reassigned); **multiple accounts for one company** (two `company_profiles` rows for the same `company_name`); **companies without a user** (orphan metadata, possible if the profile was deleted); **users without a company** (a `company` account that never created a `company_profiles` row); **resources without an owner** (an `opportunities` row whose `publisher_id` does not map to any `company_profiles` row). The backfill plan reviews each class and records the resolution; the backfill does **not** create an `organization` row for a `company_profiles` row whose mapping is ambiguous. The exact backfill query is the migration plan's responsibility (out of scope for this document).

### 5.4 Unique active owner — flow and implementation options

This sub-section formalizes the "one organization, one active owner" invariant (D-05), the transfer flow, the suspension semantics, and the implementation options. **No SQL is authored here**; the document records the intent, the flow and the candidate implementation strategies, not the schema.

- **Invariant (D-05, REV 4.2 FINAL DOCUMENTARY CLEANUP / AUDIT PENDING — at-most-one / at-least-one / exactly-one).** For `organizations.status = 'active'`, the canonical rule is **exactly one membership with `member_role = 'owner'` and `status = 'active'`** (D-05). The invariant is the combination of three derived rules: **at-most-one** (no two active `owner` memberships on the same organization; the unique partial index enforces this at the database, and "defer the index" is **not** a valid implementation option), **at-least-one** (every active organization has at least one active `owner` membership, with brief exceptions during the transfer window and the controlled recovery), and **exactly-one** (the combination; for `organizations.status = 'active'`, exactly one membership with `member_role = 'owner'` and `status = 'active'`). The initial state is one owner (the admin / founder). The mandate reserves multi-owner for a later phase; the initial UI exposes only one owner and shows a placeholder for future admins. There is no "two active owners" state. The invariant is **per-organization**, not global.
- **No shared credentials (D-06).** A person authenticates as themselves; they are bound to an organization through their membership. There is no login shared between a person and an organization. The owner membership is the only authority that grants "act on behalf of the organization" power; the same physical person who is the owner of one organization may be a member of another, and the membership is per-organization.
- **Initial state.** When a new organization is created, the migration or the first server action that creates the organization must also create the `owner` membership for the person who triggered the creation. The person is the `creator` (their `profile_id` is recorded as `created_by_profile_id` on the organization row, audit only — see §10). The owner is the same person at creation time. There is no "organization with no owner" state at any time, **except** during the brief transfer window below; the recovery state is recorded in the migration plan.
- **Transfer flow — 8 conceptual steps (rev. 4.2; canonical; supersedes the prior transfer framing and the rev. 4.1 "neutralize then promote" framing).** When the owner transfers ownership to a different person in the same organization, the **conceptual 8-step sequence** (no SQL) is:
  1. **Block the organization and its memberships.** The migration plan / server action takes the appropriate row-level lock on `organizations` (and the relevant `organization_memberships` rows) to prevent concurrent transfers on the same organization. No new writes are admitted during the transfer.
  2. **Verify the current owner.** The current owner membership exists with `member_role = 'owner'`, `status = 'active'`, `profile_id = auth.uid()`. If the check fails, abort and roll back.
  3. **Verify the successor.** The successor is a member of the same organization with `profile_id <> auth.uid()`; the successor is **not** currently `owner`; the successor's membership is in a state that allows promotion (e.g. `active` with another `member_role`, or no row). If the check fails, abort and roll back.
  4. **Create or activate the successor's membership — without `member_role = 'owner'`.** If the successor has no row, insert one with the current `member_role` and `status = 'active'`. If the successor has a row, update it to `status = 'active'`. **At this intermediate point the successor is not yet `owner`.**
  5. **Neutralize the previous owner in the same transaction.** Set the previous owner's row to `member_role = 'admin'` and `status = 'active'`. The previous owner retains `active` status and becomes `admin`; they do not lose access. The neutralization is the physical step that resolves the unique-index constraint: the partial unique index only counts rows with `member_role = 'owner' AND status = 'active'`, and after the demote the previous owner is no longer counted.
  6. **Promote the successor in the same transaction.** Set the successor's row to `member_role = 'owner'`, `status = 'active'`. The promotion happens physically after the neutralization so that, at every intermediate write, the partial unique index sees at most one `active` `owner` row.
  7. **Register the audit event.** Insert the transfer event into the audit log with `created_by_profile_id = previous_owner`. The audit records the historical actor; it does not record ownership. The application status notifications (e.g. to the organization dashboard) are emitted by the same server action.
  8. **Verify the invariant before commit.** Within the same transaction, count the `active` `owner` rows for the organization. The count must be exactly 1. If it is 0 or > 1, raise an exception and roll back. Only then commit.
- **Atomicity (rev. 4.2 — non-observable partially-applied transfer).** The 8-step sequence is a **single atomic operation** from the perspective of any external observer (RLS, another transaction, the audit log, the application). The operation is **not** partially observable: an external observer must never see a state with two active owners, a state with zero active owners, or a state in which the successor is not yet `active` `owner`. The unique partial index that enforces "at most one active owner per organization" (e.g. `UNIQUE (organization_id) WHERE member_role = 'owner' AND status = 'active'`) is **not deferrable** in PostgreSQL; therefore "defer the index" is **not** a valid implementation option. The implementation must take the appropriate lock and coordinate uniqueness and state so that the unique-index invariant (D-05, I-18) is not violated and no committed state is left in a non-invariant form. **No commit intermediate without an owner.** The transaction is the unit of atomicity; there is no commit between the demote and the promote. The neutralize-then-promote physical order is the opposite of the logical flow and is required so the previous owner is removed from the partial-index set before the successor is added. **No SQL is chosen in this document.** The migration plan chooses the concrete strategy (transactional function, server-action flow, or combination) under Gate B2.
- **Status vocabulary (status contract).** The membership status contract is **`active | invited | suspended | disabled`**. The token `revoked` is **not** a membership status; it is a logical operation recorded through `status = 'disabled'` (or `status = 'suspended'`) plus an audit / revocation timestamp in the audit log. The owner-revocation rule is therefore: **transfer first**, or **organization suspension**; a `status = 'disabled'` on the owner leaves the organization ownerless and is forbidden by the invariant except as part of a controlled exceptional recovery (see below). This vocabulary is used consistently in §7.4, §8, §10.2 and in the companion ADR.
- **Suspension of the owner (REV 4.2 FINAL DOCUMENTARY CLEANUP / AUDIT PENDING — pending / suspended / recovery states have no ordinary operations; no active ownerless ordinary state).** Suspending the owner membership (`status = 'suspended'`) does **not** auto-promote a different member. The organization does **not** enter an active ownerless ordinary state; it enters a **controlled recovery** state, with no ordinary operations (no automatic transitions, no auto-promote, no ordinary writes). The migration plan must record the recovery state: the only way to leave the ownerless controlled-recovery state is a **service-role transfer** that promotes a specific member to `owner` (a service-role action recorded in the audit log, with a documented reason and a designated successor). The Phase 1B migration must not include a "auto-promote" trigger; auto-promotion is a regression (it would re-introduce a shared-credentials anti-pattern by allowing any other member to take over). **Pending / suspended / recovery states have no ordinary operations.**
- **Revocation of the owner — controlled exceptional recovery.** "Revocation" of the owner is **not** a free operation that leaves the organization ownerless. The only sanctioned ways to leave the active-owner role are: (i) the **8-step transfer flow**, or (ii) the **suspension of the organization** (which removes all authority and is reversible only by the product-owner / service-role recovery). A direct "revoke" of the owner without transfer or organization suspension is forbidden by the invariant. The owner-revocation rule therefore **remains**: transfer first, or organization suspension; the controlled exceptional recovery path is a service-role action recorded in the audit log, with a documented reason and a designated successor. The previous framing of "revoking the owner (`status = 'revoked'`)" as a separate operation is replaced by this recovery semantics; the word `revoked` does not appear as a membership status.
- **Initial UI.** The Phase 1B UI exposes exactly one owner. The placeholder for future admins is a small read-only hint ("you can add admins later"); it does not show a list of admins and it does not allow adding admins in Phase 1B. The "admins" management is a deferred sub-phase and is not in the initial schema.
- **Implementation options (to be decided at implementation time, not in this ADR).** The four candidate strategies are recorded for traceability; **no choice is made in this document**.
  - **Option 1 — Partial unique index.** A partial unique index on `organization_memberships(organization_id)` where `member_role = 'owner' AND status = 'active'` enforces "at most one active owner per organization" at the database. The server action enforces the transfer flow. The index is a single DDL; the transfer is a single transaction. Pros: minimal, declarative, the database refuses any second active owner row. Cons: the index does not enforce the transfer flow; the application must still perform the atomic promote + demote in a single transaction.
  - **Option 2 — Transactional function.** A `SECURITY DEFINER` function `transfer_organization_owner(organization_id, target_profile_id)` that performs the promote + demote in a single transaction and raises on any invariant violation. The function is called from the server action. Pros: the function is the only path that mutates the owner row; the function is unit-testable. Cons: a `SECURITY DEFINER` function is a privileged code path; the function must declare a fixed `search_path` and minimum grants; the function is a wider surface than the index.
  - **Option 3 — Defensive trigger.** A `BEFORE INSERT OR UPDATE` trigger on `organization_memberships` that raises if the new / updated row would create a second active owner. The trigger is a safety net under options 1 and 2. Pros: catches both direct INSERTs and any function that bypasses the index. Cons: triggers are harder to reason about; the trigger can be disabled by a `session_replication_role = 'replica'` setting.
  - **Option 4 — Combination.** A partial unique index (1) AND a defensive trigger (3) AND a transactional server-action flow (server action 2 without the function) — three layers. Pros: maximum safety. Cons: highest cost; risk of over-engineering. The mandate does not require option 4; the recommendation is **option 1 + option 2 + the server-action atomic flow** (the index is the declarative guarantee, the function is the only mutation path, the server action is the user-facing wrapper).
- **What the ADR records.** The ADR records the invariant (D-05), the no-shared-credentials rule (D-06), the 8-step transfer flow (rev. 4.2), the suspension semantics, and the four implementation options as **future implementation decisions**. The ADR does **not** choose a SQL implementation, does **not** write a CHECK constraint, does **not** write a partial unique index, and does **not** write a `SECURITY DEFINER` function. The choice between options 1–4 is a migration-plan decision, gated by Gate B2 / §17.B2.

### 5.5 Authority vs ownership vs audit — recap (rev. 4.2)

- **Authority / authorization sources (rev. 4.2).** The canonical authorization source list is: `auth.uid()`; `profiles.account_status`; active `memberships`; resource ownership; `student_enrollments` (the current primary active enrollment, for student-context authorization, D-15); resource `status` / `type`; explicit contact authorization (D-38); domain relationships. The `membership` is the only thing that authorizes a person to act on behalf of an organization (D-07).
- **Ownership.** For organization-owned resources, the resource ownership column (`publisher_organization_id`, etc.) is the **reference** to the owner; the authority to act is the membership that links the actor to the owner. The `owner` membership (§5.4) is the canonical owner reference.
- **Audit source (rev. 4.2).** The audit source list is `created_by_profile_id` (D-39, D-40). The actor is the human profile that initiated the write; it is **not** the owner; it is **not** an authorization source. The actor and the owner are distinct; the membership and the actor are distinct.
- **Two disjoint lists (rev. 4.2).** Authorization sources and audit sources are **disjoint** lists. `created_by_profile_id` is in the audit list only; it is **not** in the authorization list. The historical "triad" framing of D-41 in rev. 4 / rev. 4.1 is **HISTORICAL — SUPERSEDED BY REV 4.2**: the audit column is not a member of the authorization source list. The D-41 statement in the canonical state is: "La autorización organizacional depende de `memberships` activas, ownership del recurso y relaciones explícitas de dominio. `created_by_profile_id` registra el actor histórico y no autoriza." See §10, §13.4.

### 7.4 XOR ownership invariant — formalization

This sub-section formalizes the XOR ownership rule for every resource that has an organizational vs personal owner. The rule is: **exactly one of (organization owner, profile owner) is set; never both, never neither**. The XOR is enforced at the schema level (an "exactly one of two nullable FKs" check); the RLS layer treats the set column as the source of truth.

- **General rule.** For a resource with two nullable ownership columns `*_organization_id` and `*_profile_id`, the invariant is `(*_organization_id IS NOT NULL) <> (*_profile_id IS NOT NULL)`. Both null and both set are forbidden.
- **Author and actor separation (rev. 4 clarification).** The **author** (the human who pressed the button, recorded in `created_by_profile_id` for audit, D-39) is **not** the owner. The author is the **actor**. The owner is the organization or the personal profile. In an organizational case, the author must have an active membership in the owning organization; in a personal case, the author is the personal owner. The author and the owner are distinct concepts (D-40); the membership is the bridge between the author and the organization (D-07). The membership status contract is `active | invited | suspended | disabled` (§5.4 rev. 4); the token `revoked` is not a status.
- **Posts: `author_profile_id` is the actor, NOT in the XOR (rev. 4).** For `posts`, the actor is `posts.author_profile_id` (a `NOT NULL` FK to `profiles.id`). The author is always a person. The **ownership** XOR is on `posts.organization_id`: it is `NULL` for a personal post (the author is the personal owner), or it is set for an organizational post (the organization is the owner; the author is the actor, membership-gated). **`author_profile_id` does not participate in the ownership XOR**; it is the actor, always required. If `organization_id IS NULL`, the post is personal; if `organization_id IS NOT NULL`, the post is organizational and the author is the actor, not the owner. This is the canonical posts ownership rule (D-23, D-24) and supersedes the previous "author_profile_id in the XOR" framing.
- **Opportunities: school is NOT a publisher organizacional (D-30).** The owner-invariant in the abstract supports `organizations.kind IN ('company', 'school')` as the published-by side of the XOR. However, the canonical resource `opportunities` (D-26, D-30) accepts **only `kind = 'company'`** as the publisher organizacional; **`kind = 'school'` does not publish `opportunities` of any type (`job`, `internship`, `company_project`, `freelance_request`)**. The `opportunities.publisher_organization_id` is therefore set **only** for `kind = 'company'` under the current canonical model. Any mention of a `school` organization in this document is **contextual** (school ownership of other resources, school mediation of contact requests, school validation of evidence) and is **never** a publisher of `opportunities`. The school-organization concept remains useful for `posts`, `evidence`, `validation`, and institutional workflows (D-18, D-19, D-23) but is not a publisher of commercial `opportunities`.
- **Who modifies and who deletes.** A resource is modified by the actor (the human who initiated the change, gated by membership if the resource is organizational) and is deleted by the same actor. A resource cannot be modified or deleted by a person who is neither the owner nor an authorized member. A transfer of ownership (see §5.4) does not delete the resource; it only changes the owner reference.
- **Effect of membership revocation / disable / suspension.** When a member's `organization_memberships.status` transitions to `disabled` or `suspended` (rev. 4 vocabulary; the token `revoked` is not a status), the resources the member authored are **not** deleted. The owner of the resource is still the organization. The author of the resource (`created_by_profile_id`) is still the (now disabled or suspended) person. Future edits by the disabled / suspended person are denied by the RLS layer because the membership is no longer active. Future edits by other members of the same organization are still allowed (the membership of the author is not the membership of the editor).

- **Conventions for "XOR exactly one of two nullable FKs" (rev. 4).**
  - The set column on a resource row is the canonical authority for the ownership question. The client **never** sends either FK (D-31, D-32, D-33). The server action derives the set column from the session and the membership.
  - The unset column is `NULL` (not a sentinel value, not `0`, not an empty string). PostgreSQL allows `NULL` FKs; the XOR is enforced by a check that the two FKs are not both null and not both set.
  - The RLS layer reads the set column to decide whether the resource is organizational or personal; the RLS does not inspect the `account_type` of the actor for ownership (it inspects the membership).
  - The application layer (server actions) sets the set column from the session; the client cannot override the set column. The migration that adds the two FKs is additive; the NOT NULL on the unset side is **not** added until the backfill is verified (the backfill must leave one column set and the other null, not both set or both null).
  - For `posts`, the XOR is on `organization_id` (nullable), and `author_profile_id` is the always-required **actor** that does not participate in the XOR (rev. 4).
- **Edge cases — recorded for the migration plan.**
  - **Company A's membership is `disabled` mid-resource-lifecycle.** The resource is not deleted; the owner is still Company A. The author of the resource is the (now disabled) person. Future edits by the disabled person are denied; future edits by other members of Company A are still allowed. The owner-revocation rule (§5.4) requires a prior transfer or organization suspension; a free "revoke" of the owner is forbidden.
  - **Resource created during a school mediation (D-37).** The school is the **mediator** (context, not owner) of the contact request. The school does not own the request; the requester (company or external) is the owner. The author of the request is the person who pressed the button (the actor), membership-gated.
  - **External publishes a freelance opportunity, then joins a company.** The freelance opportunity remains personal (publisher_profile_id is set, publisher_organization_id is null). The new company membership does not retroactively change the ownership of past opportunities. Each opportunity row is owned by the publisher at the time of publication.
  - **Membership `status = 'disabled'` for the author (rev. 4).** The author retains the historical `created_by_profile_id`; the owner is still the organization; future edits by the disabled person are denied; future edits by other members of the same organization are still allowed. The transition `active → suspended` or `active → disabled` is the canonical way to record a non-active state; the token `revoked` is not a status.
- **The ADR records this XOR table in §7.3 of ADR-004 (Resource Ownership) and in §8 (Invariants). The RLS and the migration implement the XOR; the document records the intent and the per-resource row.**

  - `opportunity_proposals` (freelance proposal table, with the UNIQUE `(opportunity_id, applicant_id)`).
- RLS for `job_applications` (`20260726000011_common_opportunities.sql:157-221`): insert as applicant against an open `opportunities` row or against an active `job_postings` row; select as applicant or as the publisher (matched via `job_postings` or `opportunities`).
- RLS for `opportunity_proposals` (`20260726000013_freelance_proposals.sql:24-80`): insert as an active student against an open `freelance` opportunity; select as applicant or publisher; update by applicant (withdraw) or publisher (accept/reject). The existing RLS restricts the insert to an active student; the school/company/external personas do not get the `proposals_insert_student` policy. **However, the audit must not assert that RLS alone forces the persona check** — the audit's previous claim that "RLS forces student" was an over-simplification. The school action `submitProposal` in `apps/web/src/app/actions/opportunities.ts:122-145` also checks `account_type === "student"` server-side. Both layers agree today, but the audit must record that the server action is the **application-level** school of authorization, not the RLS.
- Server actions: `applyToOpportunity` (`apps/web/src/app/actions/opportunities.ts:91-114`) inserts into `job_applications` with `opportunity_id` set and `job_id` null; `submitProposal` (`apps/web/src/app/actions/opportunities.ts:122-145`) inserts into `opportunity_proposals`. Both guard by `account_type === "student"` and `account_status === "active"`.
- The mandate's **D-34** (applications are for the three corporate types `job`, `internship`, `company_project`) and **D-35** (proposals are for `freelance_request`) record the type semantics. The structural split between the two tables (one for corporate, one for freelance) is **one of four alternatives (A, B, C, D)** that the mandate defers to a separate phase. **No alternative is selected in this pass.**
- The mandate's **D-36** says `internship_requests` is a **temporal** workflow (school approval, status `pendiente | aprobado | rechazado`); it lives alongside the canonical `opportunities` table, mapped through `opportunity_legacy_links`, and is **not** a canonical opportunity. The current `internship_requests` table already implements this shape.

### 8.2 INFERENCES

- The current state is a **split model**: corporate applications and freelance proposals live in two separate tables, with no shared metadata and no shared lifecycle. The mandate is consistent with that split as long as the split is explicit and the naming is consistent. The mandate does not require unifying the two tables; it requires naming them clearly and aligning them with the canonical `opportunities` model. The four alternatives A, B, C, D are recorded below for traceability. **None is selected in this pass; the choice is deferred to a separate phase (D-OD-1).**
- **D-34 (applications) and D-35 (proposals) are the only type-semantic decisions adopted in this pass.** The structural alternative (A, B, C, D) is its own deferred decision and **does not** block the Proposed → Accepted transition of ADR-004. The applications/proposals schema-only work is a separate gated sub-decision (Gate C, §17.C and D-OD-1 in §16). D-OD-1 is the only blocker for Gate C.
- **D-36 (internship_requests is a temporal workflow).** Already implemented; the table exists and is mapped. No further work is required in this phase.
- **D-39 (created_by_profile_id on applications/proposals)** is **absent** in the current schema. The actor is implicit (the applicant). The mandate specifies the conceptual audit column, but **applications/proposals `created_by_profile_id` is implemented only under Gate C after D-OD-1**; it is not part of the Core B1/B2 migration scope.

### 8.3 RECOMMENDATIONS

- **D-OD-1 (which alternative from §8.4) is the only blocker for the applications/proposals schema-only work.** It is **not** a blocker for ADR-004 acceptance. The audit must not assert the opposite: ADR-004 can move Proposed → Accepted on the gates defined in §17 without D-OD-1 being closed. The applications/proposals schema-only work opens in its own phase (Phase 1B-applications) with its own pre-implementation gate.
- **D-39 implementation for applications/proposals is part of Gate C after D-OD-1 (§17.C)**. The chosen alternative determines the table, the migration adds `created_by_profile_id`, backfills from the applicant, and adds NOT NULL after the backfill. It is not implemented in the Core B1/B2 migration.
- **RLS-vs-server-action evidence for D-34/D-35.** The audit must record that the existing `proposals_insert_student` RLS policy and the existing `submitProposal` server action both check `account_type = 'student'`. The two layers agree today. The audit must **not** assert that "RLS forces student" alone, because the RLS policy is currently the only row-level guard for the `proposals` table; the persona check is replicated in the server action. The Phase 1B migration must preserve the RLS policy and keep the server action as the second line of defense; the audit does not propose to remove either.

### 8.4 Alternatives (deferred; D-OD-1)

The four structural alternatives for applications/proposals are recorded here for traceability. **No alternative is selected in this phase.** The chosen alternative is decided in a separate phase (D-OD-1).

#### Alternative A — Keep the split, normalize names (smallest delta)

- `job_applications` becomes `applications` (rename). Add `created_by_profile_id` (NOT NULL → `profiles.id`) and `created_at`. Keep `(opportunity_id, applicant_id)` UNIQUE. RLS unchanged. Type restricted to `opportunity_type IN ('job', 'internship', 'company_project')` via a CHECK or trigger.
- `opportunity_proposals` is renamed `proposals`. Add `created_by_profile_id` (NOT NULL → `profiles.id`). Keep UNIQUE `(opportunity_id, applicant_id)`. RLS unchanged. Type restricted to `opportunity_type = 'freelance_request'`.
- Pros: smallest migration surface, lowest risk, no backfill beyond a column rename.
- Cons: still two tables, two sets of RLS, two sets of triggers; the application/proposal split is preserved in the schema forever.

#### Alternative B — Single table with a discriminator (unified resource)

- `applications` (new, single table) with `opportunity_id` (NOT NULL → `opportunities.id`), `applicant_id` (NOT NULL → `profiles.id`), `kind IN ('application', 'proposal')` discriminator, `proposed_amount` (NULL for `application`, set for `proposal`), `cover_letter`, `status`, `created_by_profile_id`, `created_at`. UNIQUE `(opportunity_id, applicant_id)`. CHECK: `kind = 'application' AND opportunity_type IN ('job', 'internship', 'company_project')` OR `kind = 'proposal' AND opportunity_type = 'freelance_request'`.
- `job_applications` and `opportunity_proposals` are kept as **views** over `applications` for the migration window.
- Pros: one RLS, one trigger, one audit; lifecycle is unified; status transitions can be shared; less surface area in the long run.
- Cons: requires backfill from both legacy tables; a single CHECK on `opportunity_type` requires a join that complicates the predicate; risk of a stuck migration if either backfill fails.

#### Alternative C — Single table without a discriminator (column-driven)

- `applications` (new) with the same columns as B, but the discriminator is dropped in favor of an `opportunity_type` column on the application row (denormalized). The CHECK is column-only: `opportunity_type IN ('job', 'internship', 'company_project', 'freelance_request')` and the application lifecycle is the same for all four types.
- Pros: simplest long-term surface; one RLS, one trigger; column-only CHECK is portable.
- Cons: requires a backfill from both legacy tables; the denormalized `opportunity_type` may drift relative to `opportunities.opportunity_type` if a publisher changes the type after an application is created (the current model already forbids this for `freelance` but not in general); status semantics diverge between corporate (`hired` is a possible final state) and freelance (`withdrawn` is a possible final state) and a single lifecycle is lossy.

#### Alternative D — Two tables, both first-class, with shared lifecycle helpers

- `applications` (rename of `job_applications`) and `proposals` (rename of `opportunity_proposals`) are both first-class. They each have their own audit column (`created_by_profile_id`), their own lifecycle, and their own RLS. A small `apps/web/src/lib/services/applications/` module exposes the shared lifecycle helpers (status transitions, notification templates) without merging the tables.
- Pros: each table's RLS and CHECK is type-specific and small; lifecycle semantics are not unified by force; migration is incremental.
- Cons: two tables, two RLS, two trigger sets, but with a shared helper module on the application side; the helper module is the only cross-table abstraction.

### 8.5 Open sub-decisions for the chosen alternative

- Whether `applications` retains the `student_id` column alongside `applicant_id` (current `job_applications` has both) (D-OD-2).
- Whether `proposals.proposed_amount` becomes required for `freelance_request` or remains optional (D-OD-3).
- Whether the backfill uses a SQL function or a one-shot migration script.
- Whether the `created_by_profile_id` is `NOT NULL` for new writes and how service-role backfilled rows are handled (the answer is the **identifiable actor policy** in §10.2 — there is no `ON DELETE SET NULL`; the backfill must map the actor or block the row, never silently null it).

## 9. School ↔ Student relationship (D-15, D-16, D-17, D-18, D-19)

### 9.1 FACTS

- The legacy `profiles.school_id` column is a `NOT NULL REFERENCES profiles(id)` (`20260409000001_step1_missing_columns_and_tables.sql:20`). It is still read by `apps/web/src/lib/services/contact-requests.ts:62-80` and by the school admin server action `verifySchoolOwnsStudent` (`apps/web/src/app/actions/school.ts:320-336`).
- The canonical `student_profiles.school_id` is a nullable FK → `schools(id)` (`20260726000007_canonical_identity_access.sql:99`). **The column is a compatibility / temporal / derivable / legacy adapter column** (rev. 4.2): the canonical relation lives in `student_enrollments` (D-15); the live value is **derivable** from the primary active enrollment; new policies and new server actions **do not** consult `student_profiles.school_id` for authorization.
- The canonical membership model is `school_members` (`20260726000007_canonical_identity_access.sql:64-74`) with `member_role IN ('owner', 'admin', 'teacher', 'reviewer')`.
- **D-15 (rev. 4.2 — canonical; supersedes the prior "historical only" framing).** `student_enrollments` is the **canonical** relation between a student and a school. A row with `status = 'active'` represents the **current** matrícula; rows in other statuses represent the **history**. The conceptual model is `id, student_profile_id, school_organization_id, status, is_primary, started_at, ended_at, created_by_profile_id, created_at, updated_at` with `status` initial values `pending, active, completed, transferred, withdrawn`. **Invariants:** at most one row per student with `is_primary = true` and `status = 'active'`; multiple historical rows per student are allowed; the current school is derived from the primary active enrollment; the minor mediator's school is derived from the same primary active enrollment. **No new policy and no new server action consults `student_profiles.school_id` for authorization.** `profiles.school_id` is legacy / non-authoritative and is a candidate for retirement.

### 9.2 INFERENCES

- **D-15 (rev. 4.2 — `student_enrollments` is canonical, live + history).** Not yet implemented. The migration adds the table with the conceptual columns (`id, student_profile_id, school_organization_id, status, is_primary, started_at, ended_at, created_by_profile_id, created_at, updated_at`); backfills from the current `student_profiles.school_id` rows and the legacy `profiles.school_id` rows; reconstructs the history when retrievable from past transitions; enforces the at-most-one `is_primary = true` + `status = 'active'` invariant per student. **`student_profiles.school_id` is demoted to a compatibility / derivable / adapter column** — the live value is **derivable** from the primary active enrollment; new policies and new server actions do **not** consult `student_profiles.school_id` for authorization.
- **D-16 (rev. 4.2 — school_id is not a permanent relationship; the canonical relation is `student_enrollments`).** The mandate records this explicitly: `student_enrollments` is the canonical relation; the legacy `profiles.school_id` is a deprecated pointer that is read for legacy reasons only. `student_profiles.school_id` is a compatibility / adapter column; the live value is **derivable** from `student_enrollments`.
- **D-17 (school administers the academic context, not the student profile).** The school is the administrator of the academic context (curriculum, attendance, evidence validation). The student profile itself belongs to the student. The school membership determines who can act on the school's behalf (D-07); the student row itself is owned by the student. The mandate's previous "school administers the profile" framing is corrected: school does **not** own the profile.
- **D-18 (evidence belongs to the student).** `profile_evidence.profile_id` references the student; the evidence row belongs to the student. The school's role is to **validate** (D-19), not to own the evidence.
- **D-19 (validation belongs to the school).** `profile_evidence.school_id` references the school that performed the validation; the right to validate is mediated by `organization_memberships.member_role` (D-07). The validation event itself is recorded in `profile_evidence_events`; the actor for the validation is `reviewed_by` (D-39 audit layer).

### 9.3 RECOMMENDATIONS

- D-15 is part of the Phase 1B schema work and depends on D-09 / D-10 (`organizations` and `organization_memberships`). It cannot be planned in isolation; it requires the generic organization model to exist first.
- D-16 (the canonical relation between a student and a school is `student_enrollments` (live + history; REV 4.2 FINAL DOCUMENTARY CLEANUP / AUDIT PENDING); the `student_profiles.school_id` column is a compatibility / adapter column; the `profiles.school_id` column is legacy / non-authoritative) must be enforced: the `profiles.school_id` reads in `apps/web/src/lib/services/contact-requests.ts:62` and `apps/web/src/app/actions/school.ts:332` are **legacy readers / rewrites** (never authority; REV 4.2 FINAL DOCUMENTARY CLEANUP / AUDIT PENDING); they must move to `student_profiles.school_id` once the contact-routing service is updated, and the canonical live + history contract lives in `student_enrollments`. This is a small, surgical fix and is **not** blocked on Phase 1B. The two surgical fixes are recorded in §15.1 step 0.

## 10. Audit — `created_by_profile_id` (D-39, D-40)

### 10.1 FACTS

- `application_events` has `actor_id UUID REFERENCES profiles(id) ON DELETE SET NULL` (`20260424000002_interviews_and_timeline.sql:27`). RLS `app_events_select` and `app_events_insert` at `20260424000002_interviews_and_timeline.sql:35-55` and at `20260726000003_phase3_security_alignment.sql:228-247`.
- `profile_evidence` has `reviewed_by UUID REFERENCES profiles(id) ON DELETE SET NULL` and `profile_evidence_events.actor_id` (`20260726000004_verified_profile_evidence.sql:23, 33`). The trigger `trg_fn_profile_evidence_guard` (lines 70+) sets `NEW.reviewed_by := actor_id` for the review transition.
- `interviews` has `company_id` and `student_id` (the participants) but no generic `created_by_profile_id` column. The trigger `trg_interviews_guard_immutable` (referenced in `docs/architecture/SECURITY_MODEL.md`) prevents changes to identity columns.
- `opportunities`, `opportunity_proposals`, `job_applications` have **no `created_by_profile_id` column**. The publisher (`opportunities.publisher_id`) and the applicant (`opportunity_proposals.applicant_id`, `job_applications.applicant_id`) are the implicit actors.

### 10.2 INFERENCES

- **D-39 (rev. 4.2 — `created_by_profile_id` is the actor on every relevant resource; audit only).** The mandate requires an explicit human actor on `opportunities`, on the chosen applications/proposals table (D-34, D-35) and on the other resources named in the mandate. **The actor is the human profile that initiated the write.** It is **not** the owner of the resource (the owner is `publisher_organization_id` for **company** opportunities only — D-30: school is not a publisher of `opportunities` of any type — and `publisher_profile_id` for external personal opportunities; the actor is the human who pressed the button, which may be a company admin on behalf of the company, or a service-role migration). The two concepts are distinct (D-40). **The column is audit only**; it is **not** an authorization source, not an ownership column, not a capacity column.
- **`created_by_profile_id` is audit only — reiterated (rev. 4.2).** The column is **not** an ownership column; it does not grant the referenced profile any right to edit, delete, access or transfer the resource. The column is **not** an authorization source: the RLS layer does not read `created_by_profile_id` to decide whether the current session can mutate the resource. The column is **not** a capacity column: the fact that a profile is the actor on a resource does not imply that the profile can act on behalf of any organization. The column is **read-only** at the application layer: it is set by the server action at write time and is never updated by the application. The audit and the security review use the column to reconstruct who-did-what; nothing else. The column is in the **audit source list** only; the **authorization source list** does not include it.
- **Authorization source list (rev. 4.2).** The canonical authorization sources are: `auth.uid()`; `profiles.account_status`; active `memberships`; resource ownership; `student_enrollments` (the current primary active enrollment, for student-context authorization, D-15); resource `status` / `type`; explicit contact authorization (D-38); domain relationships. `created_by_profile_id` is **not** in this list. The previous "triad" framing of D-41 in rev. 4 / rev. 4.1 is **HISTORICAL — SUPERSEDED BY REV 4.2**.
- **Example — Company A and membership revoked (rev. 4.2).** Company A's `account_type = 'company'` profile creates an opportunity in 2026 (the `created_by_profile_id` on the opportunity is the Company A admin). In 2027, the Company A admin's `organization_memberships` row transitions to `disabled` (or `suspended`); the admin **leaves** active membership. The opportunity **is not deleted**. The opportunity **is not transferred** to the new admin automatically. The `created_by_profile_id` continues to record the (now disabled / suspended) Company A admin. The opportunity is still owned by Company A (`publisher_organization_id`). The current Company A admin **can** edit the opportunity (because they are an active member of the organization — the authorization is membership-gated, not actor-gated). The (now disabled / suspended) Company A admin **cannot** edit the opportunity (because their membership is no longer active). Another active member of Company A **can** administer the opportunity. The `created_by_profile_id` is the historical record of who pressed the button; it does not grant or revoke any capability. The audit log preserves the original author; the new admin's edits are recorded on the audit events with their own `actor_id`.
- **Identifiable actor policy (rev. 4.2).** For **new writes**, `created_by_profile_id` is `NOT NULL`. The application sets it from the authenticated session (`auth.uid()`); the migration that introduces the column sets it to `NOT NULL` after the backfill is verified. The **backfill** must map the actor (publisher for `opportunities`, applicant for applications/proposals) or **block the row**; it must not silently `SET NULL` and lose the actor. Service-role backfilled rows are recorded against the **service-role operator profile** if a service-role profile exists, or against the **publisher/applicant** if not; in either case, the column is `NOT NULL` after the backfill. There is no `ON DELETE SET NULL` on `created_by_profile_id`; if the referenced profile is deleted, the row is **blocked** (the FK is `ON DELETE RESTRICT` or a soft-delete pattern is used). The mandate's previous "D-OD-4: NULL vs NOT NULL for service-role backfilled rows" is therefore **not a deferred decision**: the column is `NOT NULL` for new writes; the backfill maps the actor or blocks the row; the only operational question is which profile ID is recorded for service-role backfilled rows (recorded as D-OD-4 in §16 for traceability of the operational choice, not as a structural decision).
- **D-40 (rev. 4.2 — ownership and creator are distinct; creator is not authorization).** The mandate records two columns: the resource ownership column (`publisher_organization_id` for **company** opportunities only — D-30: school is not a publisher of `opportunities` of any type — and `publisher_profile_id` for external personal opportunities) and the actor audit column (`created_by_profile_id`). The two columns are **not** the same and are not interchangeable. The current schema has neither, but conflates them implicitly (the publisher_id is the only available signal).
- **D-41 (rev. 4.2 — single source of authorization; audit is not authorization).** The audit must record the canonical sources: **authorization sources** = `auth.uid()`; `profiles.account_status`; active `memberships`; resource ownership; `student_enrollments` (current primary active enrollment, D-15); resource `status` / `type`; explicit contact authorization (D-38); domain relationships. **Audit source** = `created_by_profile_id` (D-39). The previous framing of `account_type` as a parallel authorization source is the **transitional** state; it is replaced by the authorization source list above. The two source lists are **disjoint**. The canonical statement of D-41 in the canonical state is: "La autorización organizacional depende de `memberships` activas, ownership del recurso y relaciones explícitas de dominio. `created_by_profile_id` registra el actor histórico y no autoriza." The RLS layer reads authorization; the application layer reads ownership to display; the audit log reads the actor to reconstruct history. No column substitutes for another column in its own list.

### 10.3 RECOMMENDATIONS

- D-39 implementation is a single `ALTER TABLE … ADD COLUMN created_by_profile_id UUID NOT NULL REFERENCES profiles(id) ON DELETE RESTRICT` per resource, plus a backfill that sets `created_by_profile_id` to the publisher/applicant (whichever applies), plus the NOT NULL constraint as part of the same migration (the backfill is a single SQL function, not a multi-step application-level write, to avoid drift). The order of operations is documented in §15.2 (migration order).

## 11. Minor protection per channel (D-37, D-38)

### 11.1 FACTS

- `private.can_converse` (`20260728000002_move_rls_helpers_private.sql:9-79`) gates `messages INSERT` and `conversations INSERT` (policies at `20260726000003_phase3_security_alignment.sql:127-152` and `20260728000002_move_rls_helpers_private.sql:121-152`).
- The predicate is `is_minor_profile(role, age)` (the SQL mirror of `apps/web/src/lib/utils/is-minor.ts:1-3`: `role === 'Estudiante' && (age == null || age < 18)`). `is_minor_profile` is defined in `20260726000007_canonical_identity_access.sql` (see also the references in `20260726000004_verified_profile_evidence.sql:107` and `20260728000002_move_rls_helpers_private.sql:49-54`).
- `contact_requests` is the school-mediated channel for company ↔ minor contact (`20260705000001_contact_requests.sql`). RLS in `20260726000003_phase3_security_alignment.sql:85-125`: company INSERT, school UPDATE (approve/reject), company UPDATE (cancel), SELECT for company and school, DELETE denied, minor student does not see pending rows.
- `interviews` INSERT requires `can_converse(company_id, student_id)` (`20260705000002_interviews_privacy_rls.sql`).
- The mandate's **D-37** (transversal minor mediation) and **D-38** (authorization for contact: explicit, scoped, revocable, expirable, school-mediated for minors, opportunity-scoped) record the rules. **D-38** is more specific than the previous framing: every contact channel must be **explicit** (the contact must be a deliberate action by an authorized actor), **scoped** (the contact is limited to a specific opportunity or context), **revocable** (the contact can be withdrawn), **expirable** (the contact has a time bound), **school-mediated for minors** (the school is in the loop when the contact involves a minor), and **opportunity-scoped** (the contact is bound to a specific opportunity).

### 11.2 INFERENCES

- **D-37 (transversal minor mediation).** **Partially** observed. The `private.can_converse` predicate gates `messages`, `conversations` and `interviews`. `contact_requests` is the school-mediated path for company → minor. The notifications table is **not** gated by `is_minor`; notifications are sent to the user's own row regardless of minor status. The application status update path (`updateApplicationStatus`, `updateApplicationStatusSA` in `apps/web/src/app/actions/company.ts:58-104, 109-182`) writes a notification to the applicant on every transition; for a minor, the notification is sent to the student's own row.
- **D-37 (notifications do not break the rule).** Notifications are **the user's own row**: a notification written to a minor's `user_id` does not, by itself, expose the minor to a third party. The notification's `link` may point to an organization-scoped resource; the access to that resource is gated by RLS (e.g. `application_events` RLS for company visibility). The transversal protection therefore means: **the notification payload and the notification `link` must not leak private data that RLS would otherwise hide, and the notification must not create a new channel of contact outside the school-mediated path.** The Phase 1B migration does **not** add a trigger that blocks legitimate notifications to the student; the pending decision is the **payload/link redaction** for minor-targeted notifications, and the **absence of new contact channels**. A trigger that re-routes all minor notifications to the school queue or blocks them is **not** adopted: it would block the student's own status updates and is a regression.
- **D-38 (contact authorization: explicit, scoped, revocable, expirable, school-mediated for minors, opportunity-scoped).** The existing `contact_requests` table implements explicit + school-mediated + opportunity-scoped for company → minor. The `status` column (`pendiente | aprobado | rechazado`) is the lifecycle. A **revocation** and an **expiry** are not yet explicit fields; the `status = 'rechazado'` is the closest current mechanism, but a dedicated `revoked_at` and an `expires_at` are the target shape. The migration is recorded as a Phase 1B item (§15.6) and the decision is D-OD-6 (pending; the exact column names are deferred).

### 11.3 RECOMMENDATIONS

- **D-37 (notifications: pending decision, not a trigger).** The audit does **not** propose a trigger that re-routes or blocks legitimate notifications to the student. The pending decision is the **payload / link redaction** for minor-targeted notifications and the **policy that notifications do not create a new channel of contact** outside the school-mediated path. The decision is recorded in §16 as D-OD-7 and is owned by the product owner.
- **D-38 (contact authorization: explicit, scoped, revocable, expirable, school-mediated for minors, opportunity-scoped).** The current `contact_requests` shape implements four of the six (explicit, school-mediated, opportunity-scoped, lifecycle); `revoked_at` and `expires_at` are the deferred addition (D-OD-6). The migration is in §15.10.
- **RLS runtime staging posture (D-37, D-38).** The RLS runtime verification of the school-mediated contact authorization (D-37, D-38) is a **Gate D** concern, not a Gate A or Gate B concern. The fixtures are introduced in Gate D; the verification is run on staging; the result is the input to the production authorization.

### 12.2 INFERENCES

- **Current state vs. target state.** The audit must distinguish them. The current state is: own-writes RLS on `posts`, public reads, no organization_id on the post. The target state is: D-20..D-25 imply an `organization_id` on the post (nullable; null for personal posts, set for organizational posts), an opportunity_id on the post (nullable, D-22), and an RLS layer that gates institution-scoped writes (D-23, D-24) and excludes external posts (D-25). The migration is **not** in Phase 1B; it is its own sub-phase and is deferred. The current posts surface is therefore **covered by the gap analysis** (D-20..D-25 are listed in §14) but its schema is **not** migrated in this pass.
- **D-21 (posts are not applications / proposals).** A post is editorial; it is not an application. A post may link to an opportunity (D-22) but the link is a reference, not an application. - **D-25 (external has no posts-hub initially).** External accounts do not have a posts-hub in the initial state. The mandate reserves the possibility for the future but does not adopt it.

### 13.4 Views, grants and security principles

This sub-section records the principles that govern every view, every `GRANT` and every helper function introduced by the Core migration. The principles are independent of any specific DDL; the migration plan chooses concrete values. **Runtime grants are a Gate D concern (§17.D), not an ADR concern.**

- **Allowlist over blocklist.** Every view and every helper function exposes an explicit allowlist of columns. The default is "no columns". New columns are not exposed automatically; they are added to the allowlist when a consumer needs them.
- **No `SELECT *`.** Every view and every helper function lists its columns explicitly. `SELECT *` is forbidden in the application code that reads from views and helpers; the application code uses named selects. The verification scripts (`verify:identity-access`, `verify:opportunities`, `verify:runtime-security`) extend to enforce no `SELECT *` on the new views.
- **Three real alternatives (REV 4.2 FINAL DOCUMENTARY CLEANUP / AUDIT PENDING — supersedes the "security_definer view" framing).** The phrase "security_definer view" is **not** a category in this document. A view is either `security_invoker = true` or it runs with the implicit default; the only `security_definer` objects in this codebase are **functions**. The three real alternatives are:
- **(i) `security_invoker = true` view.** Minimum grants on the view and on the underlying base tables, column allowlist on the view and the base, and RLS. "Minimum column-level grants" means no broad grants: `PUBLIC` and `anon` receive no base-table grants, and `authenticated` receives only the explicitly required columns when an authenticated invoker view needs them. PostgreSQL still requires those minimum role-level grants for the invoker to read or write through the view; broader grants are not implied.
  - **(ii) View with owner behavior** (dedicated owner role, no `BYPASSRLS`, allowlist, minimum grants, **not** mutable by application users). Used internally where justified. This view is **not** called a "security_definer view" in this document; the dedicated owner role is the security boundary. `security_barrier` may be used when this view is a multi-table projection.
  - **(iii) `SECURITY DEFINER` FUNCTION** (REV 4.2 FINAL DOCUMENTARY CLEANUP / AUDIT PENDING). The function uses a fixed `search_path`, structured output constrained by an explicit allowlist, minimum `EXECUTE`, and audit. It is the **public** projection pattern. The public surface is the function, not a view; **no `SELECT` grants on a view for the public rows**. `security_barrier` does not apply to functions.
- **Documentary recommendation by projection type (REV 4.2 FINAL DOCUMENTARY CLEANUP / AUDIT PENDING).**
  - **Public projections (anon-readable)** = `SECURITY DEFINER` FUNCTION with allowlisted structured output, fixed `search_path`, strict allowlist, minimum `EXECUTE`, audit (REV 4.2 FINAL DOCUMENTARY CLEANUP / AUDIT PENDING; supersedes the prior "preferred implementation" framing; **not** called a "security_definer view"). The 6 public rows of the conceptual public projection table are produced through this surface. **No `SELECT` grants on a view for the public rows**; the public surface is the function, not a view.
  - **Authenticated projections** = `security_invoker = true` view with minimum grants on the view and on the base, column allowlist, RLS.
  - **Internal compatibility views** = `security_invoker = true` view by default; owner-behavior or `SECURITY DEFINER` function only when justified in the migration plan.
- **Constraints by object type (rev. 4.2).** `security_barrier` is reserved for views, including `security_invoker = true` views and owner-behavior views, when a multi-table projection requires it; it is **never used for functions**. A `SECURITY DEFINER` function uses only a fixed `search_path`, structured output with an explicit column allowlist, minimum `EXECUTE`, and audit. Strict allowlists exclude internal foreign-key IDs (`profile_id`, `organization_id`) and sensitive columns from public output. Public projections are functions with `EXECUTE`, not views with grants; authenticated invoker views use only the minimum required column-level grants; `PUBLIC` and `anon` receive no base grants.
- **Anonymous role (`anon`) reads only explicit public projections through `SECURITY DEFINER` functions (REV 4.2 FINAL DOCUMENTARY CLEANUP / AUDIT PENDING).** The `anon` role is granted `EXECUTE` **only on the 6 named public projection functions** (the rows in the table below). The `anon` role is **not** granted `SELECT` on any view or any underlying base table. The `anon` projections are the **only** public surface. The historical wording "the `anon` role is granted `SELECT` only on the 6 named public projection views" is **HISTORICAL — SUPERSEDED BY REV 4.2 FINAL DOCUMENTARY CLEANUP / AUDIT PENDING**; the canonical state is that the `anon` role is granted `EXECUTE` on `SECURITY DEFINER` functions, **not** `SELECT` on a view. The principle is incompatible with `security_invoker = true` on the same 6 rows (which would require `anon` to have direct `SELECT` on the base tables); the per-row mode is therefore `SECURITY DEFINER` function (or owner-behavior view documented as such) for those 6 rows. **No `SELECT` grants on a view are given to `anon` for the public surface.**
- **Authenticated role (`authenticated`) is NOT granted automatic blanket access.** The `authenticated` role is granted `EXECUTE` on the 6 public projection functions and `SELECT` on the named authenticated-projection views (where the RLS layer gates access per-row). For an authenticated `security_invoker = true` view, it receives only the minimum required column-level grants on the base; it receives no blanket base-table access. `PUBLIC` and `anon` receive no base-table grants. RLS on the underlying tables is the gate; the views are the gate.
- **`PUBLIC` has no unnecessary grants.** The `PUBLIC` pseudo-role has no `GRANT` on any new view, any new helper, or any underlying base table. Where a `PUBLIC` grant existed historically, the migration revokes it.
- **`search_path` is fixed in every helper function.** Every `SECURITY DEFINER` (or `security_invoker = false`) function declares `SET search_path = public, pg_temp` (or the explicit list of schemas the function reads from). The fixed `search_path` prevents a search-path attack.
- **`EXECUTE` is minimum.** Every helper function is `REVOKE ALL ... FROM PUBLIC` and `GRANT EXECUTE ... TO authenticated` (or `anon`, or `service_role`) with the **minimum set of roles** that need to call it. The function is not `GRANT EXECUTE TO PUBLIC`.
- **Runtime grants are a Gate D concern, not a Gate A or Gate B concern.** The actual `GRANT` statements, the actual `SET search_path`, the actual `REVOKE`, the actual `security_definer` attribute, the actual owner role for owner-behavior views, and the actual fixtures are Gate D concerns; the migration plan implements them. This document does not authorize any runtime grant.

### 15.12 Expand / transition / contract — conceptual framework

This sub-section records the conceptual framework that governs every step in the migration order. Every step that introduces a new column, a new table, a new view, a new value, a new role, a new membership or a new ownership column is structured as **expand / transition / contract**. The framework is independent of the specific DDL; the migration plan implements it.

- **Expand.** The new structure is added in a non-destructive way. The new column, table, view, value, role, membership or ownership column is created alongside the existing one. The new structure is **additive**: the existing structure continues to work. The new structure is **dual-written** by the application code only when the dual-write can be done in a single, central layer (a server action, a database function, a trigger) — not scattered across the application. The expand step is **idempotent**: re-running the expand migration is a no-op. The expand step is **verified**: the count of new-structure rows matches the count of legacy rows (when applicable). The expand step does **not** add a NOT NULL on the new structure; the column is nullable during the dual-write window.
- **Transition.** The application code moves to the new structure. The transition is **gradual**: a single code path at a time. The transition is **observable**: the new structure's row count grows monotonically; the legacy structure's row count does not grow. The transition is **idempotent**: re-running the transition step is a no-op (e.g. the backfill is `INSERT ... ON CONFLICT DO NOTHING`). The transition uses **stable mappings** between the legacy and the new structure (e.g. a mapping table that records the legacy id → new id). The mappings are stable: re-running the mapping does not change the new id. The transition does **not** write to the legacy structure after the dual-write window ends.
- **Contract.** The legacy structure is removed. The contract step is the **only** step that is destructive. The contract step is the **last** step in the chain; it runs only when the new structure has zero legacy readers and zero legacy writers, and the verification scripts confirm that. The contract step is **forward-only**: a contract migration cannot be rolled back without re-running the expand step. The contract step preserves the new structure's ids; the legacy ids are not migrated to the new structure (the new structure has its own ids). The contract step does not delete new-structure rows; it only removes the legacy structure. The contract step is verified by a count check: the number of new-structure rows equals the number of legacy rows at the time of the contract (no rows are lost).

#### Aditional principles for expand / transition / contract

- **No duplicates.** The expand step does not duplicate rows. If the new structure has a unique constraint, the dual-write must respect it. The application code is the gate: a single source of truth decides whether to write to the legacy or the new structure.
- **Reejecución segura (safe re-run).** Every step is safe to re-run. The expand step is a `CREATE ... IF NOT EXISTS` or equivalent. The transition step is `INSERT ... ON CONFLICT DO NOTHING` or equivalent. The contract step is `DROP ... IF EXISTS` and is gated on a verification count.
- **Checksums when viable.** When a row is migrated from the legacy structure to the new structure, a checksum (e.g. a hash of the immutable columns) is recorded on the new row. The verification step compares the checksum of the new row against the legacy row; a mismatch is a fail.
- **Filas rechazadas (rejected rows).** Rows that cannot be migrated (e.g. a legacy row whose mapping is ambiguous, a legacy row whose data violates a new check) are **not** silently dropped. They are recorded in a `migration_rejected_rows` table with the reason for the rejection. The migration plan defines the rejection rules.
- **No sobrescritura de datos nuevos (no overwrite of new data).** The transition step does not overwrite a new-structure row with a legacy-structure row. The new structure is the source of truth during the transition; the legacy structure is read-only. The verification step confirms that no new-structure row was overwritten.
- **Verificadores y reconciliación (verifiers and reconciliation).** Every step has a verifier: a SQL query or a verification script that confirms the count, the checksum and the rejection count. The verifier runs after the step and is part of the verification chain (`verify:identity-access`, `verify:opportunities`, `verify:runtime-security`).
- **Centralized dual-write layer.** The dual-write (when used) is implemented in a single, central layer: a server action, a database function or a trigger. The application code does **not** scatter dual-writes across files. The single layer is the only place that knows the dual-write is happening. The single layer is unit-testable.
- **Adapters.** The transition step uses **adapters**: the application code reads through an adapter (a function, a service, a view) that knows whether the new structure is the source of truth. The adapter is the only place that knows the migration is happening. The adapter is unit-testable.
- **Contract only at the end.** The contract step runs only after the new structure has zero legacy consumers. The verification scripts confirm the count: a `SELECT count(*) FROM legacy` returns 0 (or the legacy count is the count of rows that are not in the new structure, which is 0). The contract step is **forward-only**: a rollback requires re-running the expand step.

### 15.13 Freelance → freelance_request — expand / transition / contract

This sub-section applies the expand / transition / contract framework to the `opportunity_type = 'freelance'` → `'freelance_request'` rename (D-27). The framework is the same as the general one; the specifics are recorded here.

- **Expand.** Add `'freelance_request'` to the `opportunities.opportunity_type` CHECK constraint. Keep `'freelance'` as a legacy value. The application code is updated to **write** `'freelance_request'` for new opportunities. The CHECK is now `'job' | 'internship' | 'company_project' | 'freelance' | 'freelance_request'`. The expand migration is **additive**: it does not drop `'freelance'`. The expand migration backfills existing `'freelance'` rows to `'freelance_request'` (a single SQL function, `UPDATE ... SET opportunity_type = 'freelance_request' WHERE opportunity_type = 'freelance'`). The backfill is **idempotent** (`WHERE opportunity_type = 'freelance'`). The verification script confirms: the count of `'freelance'` rows is 0 after the backfill; the count of `'freelance_request'` rows equals the count of legacy `'freelance'` rows plus the new writes during the window.
- **Transition.** The application code moves to read and write only `'freelance_request'`. The readers are updated: the Zod schema accepts only `'freelance_request'`; the TypeScript union is `'job' | 'internship' | 'company_project' | 'freelance_request'`; the public listing filter is updated; the RLS predicates are updated to use `'freelance_request'`. The dual-write window is during the transition only: the application code accepts both values on **read** (legacy readers + new readers), but writes only the new value. The RLS predicates are updated **per server action** and **per verify script**; the predicates are not scattered across the application. The transition is **gradual**: a single code path at a time. The transition is **observable**: the count of `'freelance'` reads is monitored; when it reaches 0, the contract is ready. The transition does **not** drop `'freelance'` from the CHECK.
- **Contract.** Drop `'freelance'` from the CHECK constraint. The contract migration is the **only** migration that drops the legacy value. The contract migration is **forward-only**: a rollback requires re-running the expand migration (re-adding `'freelance'` to the CHECK). The contract migration does **not** delete any row; the legacy rows were already backfilled to `'freelance_request'` in the expand step. The contract migration does **not** change the `opportunity_id`; the rename is value-only. The contract migration is verified by `verify:opportunities`: the count of `'freelance'` rows is 0; the count of `'freelance_request'` rows is the expected count; the RLS predicates use `'freelance_request'`. The contract migration does **not** propose `proposals` rename to `opportunity_proposals`; the freelance rename is value-only, not table-rename. The proposals table is renamed (or kept) in the Phase 1B-applications work (D-OD-1).

#### Rollback semantics

- **During expand.** The rollback re-adds `'freelance'` to the CHECK (a no-op if the expand did not drop it). The application code is reverted to write `'freelance'`. The backfill is reversible (re-`UPDATE` the rows to `'freelance'`).
- **During transition.** The rollback reverts the application code to read and write `'freelance'`. The dual-write window is closed. The CHECK still allows both values.
- **After contract.** The rollback is **forward-only non-destructive**: a new migration re-adds `'freelance'` to the CHECK; the application code is reverted to read and write `'freelance'`. The `opportunity_id`s are preserved; no row is deleted. The new data written during the contract window (i.e. opportunities created with `'freelance_request'`) is preserved; the application code is the only thing that changes.
- **No `proposals` are changed by the rename.** The `opportunity_proposals` table is not renamed in the freelance rename. The freelance rename is value-only. The proposals rename is a separate concern (D-OD-1) and is not part of the freelance expand / transition / contract.
- **No `opportunity_id` is changed.** The rename is value-only; the primary key is stable.
- **Conteo antes / después.** The verification scripts record the count before and after each step. The counts are: (a) the count of `opportunity_type = 'freelance'` rows; (b) the count of `opportunity_type = 'freelance_request'` rows; (c) the count of proposals per opportunity type. The three counts are recorded at the start of the expand, after the expand, after the transition, and after the contract. A mismatch is a fail.
